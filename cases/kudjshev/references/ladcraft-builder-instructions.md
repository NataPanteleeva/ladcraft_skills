# Ladcraft Builder: рабочая инструкция для агента

Это основная инструкция по созданию и исправлению draft-навыков в конструкторе Ladcraft. Она написана как операционный playbook: что делать, в каком порядке это делать и какие проверки обязательны перед публикацией.

Документ использует стиль наших builder-инструкций как шаблон организации материала, но правила Ladcraft здесь берутся только из подтверждённых источников:

- текущая интеграция конструктора в `gptz_proto`
- `skill-function-guide.md`
- `skill-web-ui-guide.md`
- `skill-migration-guide.md`
- `openapi.json`

## Что такое draft в Ladcraft builder

Draft — это файловое представление навыка внутри workspace конструктора. Навык считается publishable только тогда, когда у него собрана корректная структура файлов и эти файлы содержат валидные данные для Ladcraft.

Рабочий draft живёт в папке:

```text
/skills_builder/<slug>/
```

`<slug>` — это идентификатор навыка. Если папка уже существует, значит draft уже есть, и его нужно исправлять на месте.

## Что считается готовым draft

Готовым можно считать только draft, в котором:

- заполнены обязательные поля `application.json`
- заполнен `skill.md`
- есть хотя бы один корректно описанный инструмент
- для каждого инструмента совпадают и не конфликтуют имена файлов
- код `tools/*.js` не обрезан и синтаксически завершён
- категория допустима в текущем окружении Ladcraft
- `tools[].resources.timeout` задан в секундах и не превышает `3600`

Если хотя бы одно из этих условий не выполнено, не говори, что draft готов к публикации.

## Модель работы

### Где разрешено работать

Работай только в:

```text
/skills_builder/<slug>/
```

Типичные файлы draft:

- `application.json`
- `skill.md`
- `.ladcraft.json`
- `tools/<tool>.json`
- `tools/<tool>.js`
- `widgets/<tool>.ejs`

### Что использовать как reference

Единственный reference-контур для конструктора — файлы в `/skills_builder/_references/` и
текущий draft в `/skills_builder/<slug>/`.

### Что делать, если draft уже существует

Если в workspace уже есть папка навыка или пользователь просит исправить существующий draft:

1. Не создавай новый навык с нуля.
2. Сначала посмотри текущие файлы draft.
3. Меняй существующую структуру минимально необходимым образом.
4. После правок перечитай критические файлы и проверь, что ничего не потеряно.

## Алгоритм работы

### Перед началом правок

1. Открой `README.md`.
2. Открой `ladcraft-builder-instructions.md`.
3. Определи, есть ли уже активный draft и какие файлы в нём лежат.
4. Выбери ближайший reference в `examples/marketplace-*/` по структуре tools/widgets.
5. Только после этого приступай к редактированию файлов.

### Если создаёшь новый draft

1. Определи slug.
2. Собери минимальную publishable-структуру.
3. Не добавляй лишние файлы, пока не собран минимальный рабочий набор.
4. Используй канонические имена файлов, совпадающие с именем инструмента.

### Если исправляешь существующий draft

1. Прочитай текущие `application.json`, `skill.md`, `tools/*.json`, `tools/*.js`.
2. Не объявляй папку пустой, пока не проверены реальные файлы.
3. Если проблема локальна, исправляй только проблемные файлы.
4. После изменения любого критического файла перечитай его целиком.

## Структура draft

### `application.json`

Содержит метаданные навыка. Для публикации особенно важны:

- `name`
- `description`
- `version`
- `category`
- `tags`
- `icon`
- `cover`

Поля `name`, `description`, `version`, `category` не должны быть пустыми.

### `skill.md`

Содержит системную инструкцию навыка. Этот файл должен быть непустым и описывать:

- что делает навык
- когда его применять
- какие инструменты использовать
- какие ограничения важно учитывать

### `tools/<tool>.json`

Содержит метаданные инструмента:

- `name`
- `description`
- `capabilities`
- `environment`
- `resources`
- `schemas`

Имя инструмента должно быть каноническим и совпадать с файловым basename.

### `tools/<tool>.js`

Содержит код инструмента. Этот файл критичен для publish: если он обрезан, невалиден или пуст, публикация не пройдёт.

### `widgets/<tool>.ejs`

Опционален. Используется, если инструмент возвращает виджет.

### `.ladcraft.json`

Служебные метаданные draft, например связь с опубликованным приложением. Этот файл не заменяет содержимое skill-файлов и не делает draft готовым сам по себе.

## Как выбирать примеры

### Как выбирать marketplace reference

Используй `examples/marketplace-*/`, выбирая папку, которая:

- ближе всего по типу инструментов (API/data-heavy vs UI-heavy);
- содержит похожую глубину структуры в `tools/*.json` и `tools/*.js`;
- при наличии виджетов имеет сопоставимую сложность `widgets/*.ejs`.

### Как использовать примеры правильно

- Используй их как ближайший структурный reference.
- Не копируй бездумно все поля и значения.
- Подтверждай, что категории, лимиты и `resources` подходят текущему навыку.

## Правила для tool-функций

Подробные технические правила смотри в `skill-function-guide.md`. Ниже только рабочая выжимка, обязательная для builder flow.

### Базовый формат

Функция должна быть объявлена как:

```javascript
async function handler(state, params) {
	return {};
}
```

### Что нельзя делать

- Не используй `import` и `require`.
- Не пиши код, который зависит от неподтверждённых глобалов.
- Не оставляй синтаксически незавершённые блоки.

### `resources.timeout`

Для Ladcraft:

- `tools[].resources.timeout` задаётся в секундах
- допустимый диапазон: от `1` до `3600`
- `30000` означает `30000 секунд`, а не `30 секунд`

Если нужен таймаут 30 секунд, записывай:

```json
{
	"timeout": 30
}
```

Не используй millisecond-style значения.

### Сеть

`resources.network.hosts` должен отражать реальные внешние хосты, которые нужны инструменту. Не оставляй хосты случайными и не добавляй ненужные домены.

## Publish readiness

Перед публикацией проверь:

1. Есть ли непустой `application.json`.
2. Есть ли непустой `skill.md`.
3. Есть ли хотя бы один tool с непустыми `name`, `description`, `function`.
4. Валиден ли `category`.
5. Не превышает ли `resources.timeout` значение `3600`.
6. Нет ли обрезанных `tools/*.js`.
7. Нет ли stale или конфликтующих tool-файлов.

### Что считать конфликтом

Конфликтный случай:

- два разных файла фактически описывают один и тот же `tool.name`
- basename файла и `tool.name` расходятся
- старые файлы остались после переименования инструмента

Предпочитай каноническую схему:

```text
tools/play_snake_game.json
tools/play_snake_game.js
widgets/play_snake_game.ejs
```

где `name` внутри metadata тоже равен `play_snake_game`.

## Типичные ошибки и как их понимать

### `Приложение не найдено`

Часто означает stale `applicationId` или устаревшую связь с уже несуществующим опубликованным приложением. Не делай из этого вывод, что draft целиком пропал. Сначала сверяй `.ladcraft.json` и текущее состояние draft.

### Невалидная категория

Если publish сообщает, что категория недоступна, это не проблема виджета или tool-кода. Нужно заменить `application.category` на одно из реально доступных значений текущего Ladcraft-окружения.

### `resources.timeout > 3600`

Это означает, что в одном из `tools[].resources.timeout` стоит значение больше допустимого лимита. Обычно ошибка возникает, когда секунды путают с миллисекундами.

### Обрезанный `tools/*.js`

Если код заканчивается посреди выражения, блока или строки, publish может падать с непрозрачной серверной ошибкой. В таком случае сначала перечитай файл целиком и убедись, что он сохранён полностью.

### Сырые SQL/internal ошибки Ladcraft

Сообщения вида `Failed query`, `marketplace_application` или raw SQL — это не полезная диагностика бизнес-уровня. Обычно это только симптом того, что payload навыка уже невалиден. В таком случае проверь:

1. категорию
2. timeout
3. обязательные поля
4. целостность `tools/*.js`
5. конфликты в tool-файлах

## Best practices

- Сначала собирай минимально рабочую структуру, потом расширяй.
- Держи tools простыми: чем меньше логики зашито в tool-код, тем легче сопровождать draft.
- Решения по оркестрации лучше принимать на уровне агента, а не усложнять tool-функции без необходимости.
- Используй канонические имена файлов, совпадающие с `tool.name`.
- После каждой значимой правки перечитывай итоговый файл, а не полагайся на предположение, что запись прошла полностью.
- Если исправляешь существующий draft, сохраняй уже рабочую часть структуры и меняй только нужное.

## Anti-patterns

- Создавать новый навык, когда пользователь просит исправить существующий draft.
- Объявлять папку пустой, не проверив реальные файлы в workspace.
- Править файлы вне `/skills_builder/` вместо draft в `/skills_builder/<slug>/`.
- Ставить `resources.timeout: 30000` в расчёте на миллисекунды.
- Оставлять после переименования stale `tools/*.json`, `tools/*.js`, `widgets/*.ejs`.
- Говорить, что draft готов, не перепроверив обязательные файлы и ключевые ограничения publish.

## Worked examples

### Минимальный skill

Подходит для простого tool-less или почти tool-less сценария:

- заполни `application.json`
- заполни `skill.md`
- если нужен tool, добавь один минимальный инструмент с корректными metadata и `handler`

### Навык с одним инструментом

Подходит для data/API-задачи:

1. Возьми ближайший `examples/marketplace-*/` как reference.
2. Создай один инструмент.
3. Проверь `schemas`, `resources`, `network.hosts`.
4. Убедись, что `tools/<tool>.json` и `tools/<tool>.js` согласованы по имени.

### Widget-heavy или game-like навык

Подходит для интерфейсно насыщенного сценария:

1. Возьми ближайший `examples/marketplace-*/` как reference.
2. Сначала проверь структуру `application.json`, `skill.md`, tool metadata.
3. Затем собирай `widget.ejs`.
4. После правки виджета обязательно перепроверь, что tool-функция и widget по-прежнему связаны одним каноническим именем.

## Troubleshooting

| Если видишь              | Сначала проверь                                                    |
| ------------------------ | ------------------------------------------------------------------ |
| Draft кажется пустым     | Реальный список файлов в `/skills_builder/<slug>/`                 |
| `Приложение не найдено`  | `.ladcraft.json`, meta, связь с опубликованным приложением         |
| Категория недоступна     | `application.category` и список допустимых категорий               |
| `must be <= 3600`        | `tools[].resources.timeout`                                        |
| Raw SQL / internal error | целостность payload, timeout, категорию, обязательные поля         |
| Tool не публикуется      | `tools/*.json`, `tools/*.js`, совпадение `tool.name` и имён файлов |
| Виджет не находится      | наличие `widgets/<tool>.ejs` и каноническое имя инструмента        |

## Финальная проверка перед заявлением о готовности

Перед тем как сказать, что навык готов:

1. Открой и перечитай `application.json`.
2. Открой и перечитай `skill.md`.
3. Открой и перечитай каждый `tools/*.json`.
4. Открой и перечитай каждый `tools/*.js`.
5. Убедись, что timeout задан в секундах и не больше `3600`.
6. Убедись, что нет stale duplicate tool-файлов.
7. Только после этого сообщай, что draft готов к публикации.
