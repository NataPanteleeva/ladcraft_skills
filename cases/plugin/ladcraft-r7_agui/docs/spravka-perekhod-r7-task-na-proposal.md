# Справка для руководства

**Тема:** переход от схемы `r7.task` к схеме `r7.proposal` и локальному применению правок плагином (intent-apply).

**Контур:** плагин R7 Office `ladcraft-r7_new` и агент Ladcraft **LCA** («Лингвистическая проверка текстов»).

**Дата:** июль 2026.

**Назначение:** кратко объяснить, что изменили, как сейчас ходят данные между R7 и Ladcraft, и почему выбран новый подход.

---

## 1. Краткий вывод

| Аспект | Было (`r7.task`) | Стало (`r7.proposal` + intent-apply) |
|--------|------------------|--------------------------------------|
| Кто меняет документ | Часто агент через скрытый JSON `r7.task` (плагин авто-применяет) или кнопки после «вставить» | Плагин локально после явного согласия («вставь», «исправь все» и т.п.) |
| Что видит пользователь | Служебный JSON часто скрывали; риск правок «само собой» | Черновик / таблица в чате + скрытый proposal; документ не меняется до одобрения |
| Нужен ли ход к агенту на «вставь» | Часто да (ещё один turn) | Нет — плагин применяет proposal сам |
| Роль `r7.task` и write-tools | Основной канал правок | Fallback (нет proposal, команда «замени X на Y») |

**Итог:** агент предлагает правки; плагин вносит их в Word/Cell только после подтверждения пользователя. Меньше риска случайных изменений, быстрее UX, нет лишнего запроса к модели на каждое «вставь».

---

## 2. Контекст: плагин и три блока

Плагин Ladcraft в R7 Office (Word/Cell) — боковая панель чата с AI-агентом.

1. **Transfer** — передать контекст открытого документа в Ladcraft.
2. **Chat** — диалог (сообщения, SSE/poll, виджеты).
3. **Apply** — применить результат агента обратно в редактор.

Новая схема меняет в первую очередь блок **Apply** и контракт ответа навыка. Передача документа (Transfer) сохраняет прежние принципы (snapshot / disk-ref).

---

## 3. Как было: схема `r7.task`

### 3.1. Идея

Агент в ответе отдавал служебный fenced-блок с именем `r7.task` и JSON-массивом команд, например:

- `search_replace` — поиск и замена в документе;
- `paste_text` — вставка текста;
- другие типы по контракту r7-export.

Плагин парсил JSON и:

- для части типов (`search_replace`, `paste`, `replace_selection` и др.) — **сразу** применял к открытому документу;
- для deliver/export — показывал кнопки «Вставить» / «Скачать» только после фразы пользователя «вставить» / «скачать» (intent-gated UI).

### 3.2. Проблемы для продукта

1. **Confirm-before-write слабо соблюдался** — часть правок уходила в документ без явного «да».
2. **Служебный канал смешивался с UX** — пользователь видел текст в чате, система опиралась на скрытый `r7.task`.
3. **Лишние ходы к агенту** — на «вставь» часто уходил ещё один запрос в Ladcraft.
4. **Сложно объяснить**, кто владелец изменения документа — агент или плагин.

Эта схема остаётся в линейке `ladcraft-r7_btn_stream` / compare-сценариях. Для **LCA** выбран другой контракт.

---

## 4. Как стало: `r7.proposal` + intent-apply

### 4.1. Dual payload (двойной ответ навыка)

В одном сообщении ассистента два слоя:

| Слой | Назначение | Видит пользователь |
|------|------------|--------------------|
| Markdown (черновик, таблица «Было → Стало») | Человекочитаемый результат | Да |
| Блок `r7.proposal` (версия v1) | Машиночитаемое «что вставить/заменить» | Нет (UI скрывает) |

Пример структуры ответа навыка (логически):

1. Заголовок **Черновик:** и полный текст для человека.
2. В конце — JSON в блоке `r7.proposal` с полями `schema`, `kind`, `op`, `text` (и др.).

**Инвариант:** без валидного `r7.proposal` плагин не вставляет «всё окно чата» и не угадывает текст эвристиками. В proposal лежит **полный** вставляемый фрагмент.

### 4.2. Виды proposal

| kind | Сценарий LCA | Действие плагина после согласия |
|------|--------------|----------------------------------|
| `blob` | Черновик, саммари, перепись | `paste_text` / `replace_selection` (MD→HTML) |
| `findings` | Таблица замечаний проверки | `search_replace` по пунктам («исправь все» / «исправь 1, 3») |
| `cell_map` | Значения ячеек | `cell_paste` |
| `comment` | Комментарий рецензента | `add_comment` (нужно выделение) |

### 4.3. Intent-apply: одобрение без хода к агенту

Пользователь пишет: «вставь», «в конец», «да», «замени», «исправь все».

Плагин:

1. Распознаёт фразу (intent).
2. Берёт последний валидный proposal из истории чата.
3. Применяет его к документу через API редактора R7.
4. Показывает статус в UI.
5. **Не** отправляет это как новое задание агенту (нет ожидания ответа модели на apply).

Write-tools агента и `r7.task` — только **запасной** канал.

### 4.4. Обратная связь агенту (`r7.event`)

После успешного apply плагин может тихо отправить в сессию служебный блок `r7.event` (`apply_result`), чтобы агент не повторял apply. Пользователю блок не показывают.

## 5. Как передаются данные в Ladcraft

Блок Transfer — без принципиальной смены архитектуры.

**Цепочка:**

1. Открытый документ R7.
2. Плагин готовит `OutboundTransfer`.
3. В `content` — текст задания пользователя и при необходимости supplement (диск / snapshot path / выделение).
4. В `mentioned.files` — ссылка на документ:
   - **disk-ref:** `file_id = r7-disk:{id}` (тело файла плагин не грузит);
   - **VFS:** JSON `r7-snapshot/v1` в session VFS (plain text в `body.text`).
5. `POST /v1/agent/message` → сессия агента Ladcraft.

**Для LCA** предпочтителен **VFS snapshot:** плагин снимает текст из редактора, кладёт JSON в session VFS; агент читает `body.text`.

**Важно для руководства:**

- В message не уходит полный Word как HTML.
- В контекст модели попадает текст (plain / markdown).
- Оформление при обратной вставке восстанавливается из markdown (заголовки, таблицы, жирный) через MD→HTML и `PasteHtml` в Word.

---

## 6. Как передаются данные из Ladcraft в документ

**Цепочка:**

1. Агент / навык LCA отвечает: markdown для человека + скрытый `r7.proposal`.
2. History сессии (GET / SSE).
3. Плагин показывает черновик в чате.
4. Пользователь: «вставь» / «исправь все» и т.д.
5. Intent-apply локально в плагине (paste, replace, search_replace, cell_paste, comment).
6. Открытый документ R7 (Asc API).
7. Опционально: тихий `r7.event` в сессию Ladcraft.

**На «вставь» в нормальном сценарии не происходит:**

- повторный цикл «агент снова пишет r7.task»;
- вставка текста из статуса «Агент выполняет запрос…»;
- изменение документа без согласия пользователя.

## 7. Сравнение потоков

### Было (упрощённо)

1. Пользователь: «проверь текст».
2. Агент: замечания + скрытый `r7.task`.
3. Плагин сразу (или после ещё одного хода) правит документ.
4. Риск: пользователь не успел согласовать формулировки.

### Стало (LCA)

1. Пользователь: «проверь текст».
2. Агент: таблица «Было | Стало» + `r7.proposal` (findings). Документ не тронут.
3. Пользователь: «исправь все» или «исправь 1, 3».
4. Плагин локально применяет замены. Агент не вызывается.
5. Статус в UI; при необходимости агент получает `r7.event`.

Для генерации и саммари: сначала черновик, затем «вставь» → paste в Word.

---

## 8. Почему так сделали

1. **Безопасность документа** — правки только после явного согласия (ТЗ LCA, confirm-before-insert).
2. **Прозрачность** — виден согласованный черновик, а не «магия» JSON.
3. **Скорость и стоимость** — одобрение не тратит токены модели.
4. **Разделение ролей:** агент — лингвистика и предложение текста; плагин — запись в R7.
5. **Совместимость** — `r7.task` / write-tools остаются fallback; compare-линейка на прежнем контракте.
6. **Предсказуемость** — без proposal плагин не вставляет.

## 9. Что сделали в работах

| Область | Изменение |
|---------|-----------|
| Плагин | Форк `ladcraft-r7_btn_stream` → `ladcraft-r7_new` под LCA |
| Контракт навыка | Основной канал: `r7.proposal/v1` |
| Apply | Модуль intent-apply: фразы пользователя → локальный Asc без turn к агенту |
| UI | Action bar, статусы apply, скрытие proposal |
| Feedback | Тихий `r7.event` (`apply_result`) |
| Fallback | `tool_calls` / `r7.task` |
| Агент LCA | Instruction и навыки на proposal; write-tools на шаге «черновик» запрещены |
| Transfer | VFS snapshot для LCA; disk-ref для disk-агентов |

Документация: `docs/03-apply-rules.md`, `docs/04-skill-output-contract.md`; `cases/LCA/agent/instruction` и SKILL.md навыков.

## 10. Что не меняли

- Авторизацию и каталог агентов Ladcraft.
- Трёхблочную архитектуру плагина.
- Принцип: тело документа не кладётся целиком в `content` сообщения.
- Сценарии сравнения документов (compare-r7) — отдельная линейка с `r7.task` / deliver по своим правилам.

## 11. Риски и митигации

| Риск | Митигация |
|------|-----------|
| «Вставь» без proposal | Статус «нет proposal»; не вставляем мусор |
| Нет выделения при replace/comment | Статус «выделите фрагмент» |
| Агент вызвал write-tool | Fallback: tool_calls / r7.task с дедупликацией |
| Путаница со старым плагином | LCA → `ladcraft-r7_new`; compare → своя сборка |

---

## 12. Рекомендации для руководства

1. Для «Лингвистической проверки» канон: **ladcraft-r7_new + LCA + r7.proposal**.
2. Не требовать от LCA основной путь через `r7.task` — это регресс.
3. На демо: черновик в чате → фраза согласия → изменение в Word без ожидания агента.
4. Сравнение документов вести отдельно; не смешивать KPI с LCA apply.

## 13. Глоссарий

| Термин | Смысл |
|--------|--------|
| r7.task | Старый служебный JSON: прямые команды редактору |
| r7.proposal | Машиночитаемый черновик действия; после согласия |
| Intent-apply | Плагин применяет proposal по фразе пользователя |
| r7.event | Уведомление агенту о результате apply |
| Dual payload | Markdown для человека + скрытый proposal |
| VFS snapshot | JSON-снимок текста в session Ladcraft |
| disk-ref | Только id файла на Р7-Диске (`r7-disk:{id}`) |
